# M4.5 — Live recon: real postings, real fill, real findings

> **For agentic workers:** This is an operational/research plan, not a TDD
> code plan — most steps are commands to run and observations to record, not
> tests to write. Use superpowers:executing-plans to work it task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the empty "Live results" tables in `docs/ats/findings.md`
with real rows from real Greenhouse and Lever application forms, run against
the **repaired** extension (M4.6 must land first — the point of this pass is
to confirm those fixes hold outside jsdom, not to re-discover the same four
bugs). The output of this plan is what unblocks M5 per `PLAN.md`: adapter
selectors are written from these rows, never guessed.

**Architecture:** Two phases that need different tools, run by whichever
executor actually has that capability:

- **Phase A — find and vet postings.** Needs live web search, not a browser.
  This is the part the user asked to run through **Codex CLI with the
  `gpt-5.6-tera` model** (confirmed installed at `codex-cli 0.145.0`,
  confirmed to support `--search` for live web search this session).
- **Phase B — drive the browser and fill.** Needs a real Chrome session
  running the built extension. Codex has no browser tool for this — it must
  run through Claude Code's `mcp__claude-in-chrome__*` tools, or the user
  doing it by hand with the existing checklist in `docs/ats/findings.md`.

**Tech Stack:** `codex exec --search`, Claude Code's Chrome automation
tools, the already-built `@jaf/extension`.

**Spec:** `docs/superpowers/specs/2026-09-13-job-application-filler-design.md`
§3, §4. This plan produces the input `PLAN.md`'s M5 row requires; it does not
implement any spec section itself.

## Global Constraints

- **Never auto-submit.** Every posting used here is filled and reviewed, then
  left on the form page — the Submit button is never clicked, by design
  (`fill/guard.ts` already refuses it; this plan does not test around that).
- **Never commit `profile/`.** Use the real profile already in `profile/` on
  this machine, or a disposable throwaway profile — either way, nothing under
  `profile/` gets added to git.
- The server binds `127.0.0.1` only, every request needs the pairing token —
  unaffected by this plan, just don't work around it.
- Record real markup and real outcomes in `docs/ats/findings.md`. Do not
  invent or guess at DOM structure for a site not actually opened.

## Task 3: Independently verify each candidate URL

Codex's own search result is not itself verification — confirm it here,
since a stale or hallucinated URL wastes the whole browser pass in Task 4.

- [ ] **Step 1:** For each URL from Task 2, fetch it and check for a real
  application form, not a 404 or a "position closed" page:

```bash
curl -sL -o /dev/null -w '%{http_code}\n' '<url>'
```

Expected: `200`. Anything else (404, 410, a redirect to a generic careers
listing) means the posting is gone — go back to Task 2 with a note that this
one failed, and ask for a different one.

- [ ] **Step 2:** If `curl` returns `200`, fetch the body and grep for the
  form:

```bash
curl -sL '<url>' | grep -io 'greenhouse\|lever\|application' | sort -u
```

Expected: at least one hit. Greenhouse and Lever both render a good amount
of their form server-side or in an easily-detected embed script; a totally
empty result here is a sign the posting needs a browser to render at all
(not disqualifying, just something to note before Task 4).

## Task 4: Run the extension against each verified posting (Chrome)

This phase needs a real browser. Run it via Claude Code's
`mcp__claude-in-chrome__*` tools (load them first with one `ToolSearch` call:
`select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__tabs_create_mcp,mcp__claude-in-chrome__get_page_text,mcp__claude-in-chrome__read_console_messages`),
or hand this section to the user as the existing manual checklist in
`docs/ats/findings.md` if no browser tool is available in the session.

- [ ] **Step 1: Start the app**

```bash
npm run dev
```

Confirm server on `4321`, controller on `5173`.

- [ ] **Step 2: Load the extension**

Navigate Chrome to `chrome://extensions`, enable Developer mode, "Load
unpacked", select `packages/extension/dist`. Note the extension ID.

- [ ] **Step 3: Pair**

Navigate to `http://localhost:5173`, open the **Setup** tab, copy the token.
Open the extension's Options page, paste the token, click "Save and test".
Confirm it reports paired (this is also a live check of M4.6 Task 1 — the
Setup page's own "Local AI" section should now show a "Checking…" state
immediately after clicking Re-check, not go silent).

- [ ] **Step 4: Confirm the profile has test data**

In the controller's Profile tab, confirm first name, last name, email, and
phone are filled in. Add one resume in the Resumes tab if none exists.

- [ ] **Step 5: Greenhouse pass**

Navigate to the verified Greenhouse URL. For each item, record pass/fail and
outer HTML of anything that failed (DevTools → right-click element → Copy →
Copy outerHTML):

  - [ ] FAB "Fill application" appears (note if a second FAB appears in an
    iframe — this is the known cross-frame gap, expected, not a new bug)
  - [ ] Click Fill — first name, last name, email, phone populate correctly
  - [ ] Review panel opens with correct filled/attention counts
  - [ ] Any dropdown/combobox question (e.g. "How did you hear about us?")
    — confirm the value written is one of the real visible options, not
    free text. This is the specific M4.6 Task 4 fix — check it carefully.
  - [ ] Any open-ended question (e.g. "Why do you want to work here?") — AI
    fills it, or shows a `needs-user` row with a **specific** reason (not
    the old generic "server offline"). This is the M4.6 Task 2 fix.
  - [ ] Honeypot / hidden fields untouched (DevTools → inspect, confirm no
    unexpected values)
  - [ ] Submit button never clicked — page stays on the form
  - [ ] Edit the phone field by hand, click Fill again — your edit survives
  - [ ] Read the extension's console (`read_console_messages`) for errors

- [ ] **Step 6: Lever pass**

Same checklist as Step 5, on the verified Lever URL.

- [ ] **Step 7: Negative control**

Navigate to `https://example.com` — confirm no FAB appears.
